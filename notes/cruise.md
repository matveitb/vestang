# Круиз-контроль в M74.9: как включается

## Итог

Круиз включается **только калибровками**. Код не меняется ни на байт.

| Софт | что менять | сколько байт |
|---|---|---|
| I862BB03 | `0x63BEA` = 01, `0x63BEB` = 01 | 2 |
| I862BB04 | `0x63BE9` = 01, `0x63BFA` = 01, `0x63BFB` = 01 | 3 |
| I865BB02 | уже включено с завода | — |

Плюс пересчёт КС калибровок в `0x7FFFC`.

| адрес (BB04) | адрес (BB03) | назначение |
|---|---|---|
| `0x63BE9` | `0x63BD9` | признак поддержки круиза |
| `0x63BFA` | `0x63BEA` | круиз-контроль |
| `0x63BFB` | `0x63BEB` | ограничитель скорости |

У BB03 весь блок сдвинут на `-0x10`, и признак поддержки там уже выставлен
с завода — поэтому хватает двух байт. У BB04 признак поддержки нужно
доставить самому.

## Доказательство

Пары тюнера `+tun` против `+tun KK` — одна база, один тюнинг, различие
только в круизе:

```
I862BB04_Vs008_70_E2+tun.bin -> ... KK.bin   (7 байт)
  063BE9  00   -> 01
  063BFA  0000 -> 0101
  07FFFC  КС калибровок пересчитана

I862BB03 E2+tun.bin -> ... KK.bin            (6 байт)
  063BEA  0000 -> 0101
  07FFFC  КС калибровок пересчитана
```

`tools/ccflag.py on` воспроизводит оба файла тюнера **байт в байт**.

## Опознание блока без A2L

Блок находится по соседям в таблице калибровок, без привязки к адресам:

```
#n-5 = 03FF      #n-4 = признак поддержки    #n-3 = 00000046
#n-2 = 40        #n-1 = 03                   #n = круиз   #n+1 = ограничитель
```

Остальное содержимое блока (`#204..#211`, `#214`) во всех 27 образах
побайтно идентично: `26`, `200`, `200`, `[3,255]`, `[0,0x4600,64,-64]`,
`64`, `3`, `0`. Значения `26 / 200 / 200` по порядку величины похожи на
пороги скорости, но масштаб **не подтверждён** — без A2L это догадка.

## Два стиля работы с КС

| Тюнер | Компенсатор `0x7FFF8` | КС `0x7FFFC` |
|---|---|---|
| файлы `S_CVN...` | подбирает, чтобы КС осталась **заводской** | не меняется |
| файлы `...+tun` | не трогает (`FFFFFFFF`) | **пересчитывает честно** |

`ccflag.py` по умолчанию пересчитывает честно; с ключом `--pin` сохраняет
заводскую КС компенсатором.

## Инструмент

```sh
python3 tools/ccflag.py show firmware/original/*.bin
python3 tools/ccflag.py on  вход.bin выход.bin          # честный пересчёт КС
python3 tools/ccflag.py on  вход.bin выход.bin --pin    # сохранить заводскую КС
```

## Что оказалось неверно (исправлено)

- **«На BB04 одних флагов недостаточно, нужен ещё блок `#224..#228`».**
  Неверно. Блок `#224..#228` (в BB04 пары схлопнуты в одинаковые значения)
  тюнер не трогает вообще — хватает трёх байт. Схлопнутые пары там
  относятся к чему-то другому, а не к готовности круиза.
- **«Круиз активируется конфигурированием ЭБУ через сканер».**
  Неверно, включается прошивкой. Предположение строилось на том, что блок
  не адресуется кодом напрямую, — но это говорит лишь о способе доступа.

## Код круиза — найден

Найден эмуляцией: `tools/emu_fuzz.py` прогоняет инициализацию, снимает
снапшот RAM и вызывает каждую функцию прошивки, отслеживая обращения
к блоку. Из 1200 проверенных функций блок читают 11:

| функция | что читает |
|---|---|
| `0x860F8` | почти весь блок + карты `0x63C00` / `0x63C10` — основная логика |
| `0x8458C` | `63BE6`, `63BF8`, `63BFA`, `63BFB`, `63BFD` |
| `0x84360`, `0x8645C` | `63BFA`, `63BFB`, `63C20` — проверка флагов |
| `0x83760`, `0x86064` | `63BE2`, `63BE4`, `63BFC` |
| `0x82E80` | `63C00`, `63C10` |
| `0x84100`, `0x86304`, `0x99CF8` | `63BE2` |

В `0x84360` видна логика опроса кнопок: маска из `SRAM+0x1560`
проверяется по битам `tst.w sl, #1 / #2 / #4 / #8`, плюс состояния
из `SRAM+0x1526`, `0x1528`, `0x1529`, `0x152A`.

## Почему статический поиск был бессилен

Код **никогда не держит адрес калибровки**. Доступ идёт через геттер
`flash+0x48DC` с двойной косвенностью:

```
0048DE  ldr.w r0, [r0, r1, lsl #2]   ; дескриптор = таблица[индекс]
0048E2  ldrb  r3, [r0, #1]           ; тип из дескриптора
        ... bl 0x3E2A / 0x3E38 / 0x3EB2   ; читатель по типу
```

Вызов в функции круиза: `r0 = 0x080416D4` (база таблицы), `r1 = 0x574`.

Дескриптор, 12 байт:

```
+0 флаги | +1 тип | +2 разрядность | +4 количество (4 б) | +8 указатель на значение
```

Индексы флагов (одинаковы во всех трёх софтах):

| калибровка | дескриптор (BB04) | индекс |
|---|---|---|
| круиз `0x63BFA` | `0x4A8D4` | `0x574` |
| ограничитель `0x63BFB` | `0x4A8E0` | `0x590` |
| признак поддержки `0x63BE8` | `0x4A8A4` | `0x973` |
| порог `0x63BE0` | — | `0x597` |
| порог `0x63BE2` | — | `0x598` |

`tools/caltable.py <файл> <адрес>` проходит цепочку от адреса калибровки
к дескриптору и индексу.

## Исправление к прежнему выводу

Ранее в заметках стояло «к блоку `0x63BD0..0x63C23` нет обращений ни в одном
сегменте кода». Это неверно: обращения есть, но адрес вычисляется в
рантайме из таблицы, поэтому поиск литералов, `movw/movt` и базы со
смещением их принципиально не видит. Из того же заблуждения выросло и
предположение про активацию сканером.

Заодно была неверно разобрана структура дескриптора: указатель лежит на
`+8`, а не в начале записи, из-за чего прежний парсер читал поля
«тип/флаги/количество» от следующей записи. `caltable.py` переписан,
`ccflag.py` переведён на байтовую сигнатуру блока и не зависит от разбора
таблиц — после переписывания он по-прежнему воспроизводит оба файла тюнера
байт в байт.

## Стенд эмуляции

`tools/emu.py` — прогон старта (Unicorn, Cortex-M4, флеш `0x08000000`,
SRAM `0x20000000`). Периферия отдаёт все единицы, иначе инициализация
зависает на флагах готовности; флаги, которые в железе ставит прерывание,
подставляются после 200 чтений нуля.

`main()` после инициализации крутится в пустом цикле (`0x1418 ↔ 0x141C`) —
вся работа M74.9 идёт в прерываниях и задачах, поэтому чтения калибровок
при простом прогоне не видно вовсе. Обработчики из таблицы векторов
(32 штуки) блок тоже не читают: они только ставят флаги. Сработал именно
перебор функций.

## Состав модуля круиза

Граф вызовов (`tools/callgraph.py`) показывает две независимые подсистемы,
каждая висит на своей задаче планировщика (задачи корневые — их никто не
вызывает через `bl`, планировщик берёт их по таблице):

```
задача 0x96CEC
 └─ 0x860F8   регулятор: главная логика
     ├─ 0x82E80   карты 0x63C00 / 0x63C10 (±824…±1848) + 0x63BEC, 0x63CDC,
     │            0x63CE0, 0x63DA0 — массивы через геттер 0x4978
     ├─ 0x8458C   основной набор: 0x63BE6, 0x63BF8, 0x63BFA, 0x63BFB,
     │            0x63BFD, 0x63D14, 0x63D20, 0x63CEA, 0x633B8, 0x633BB
     └─ 0x8515C   0x63BF0 (массив ±64, n=4), 0x63D10, 0x63D1E, 0x63CE6
 └─ 0x86064 → 0x83760   пороги 0x63BE2, 0x63BE4, 0x63BFC

задача 0x9A530
 └─ 0x8645C   состояние и индикация (SRAM 0x15F0…0x15F2, 0x3B9B…0x3BA2)
     ├─ 0x84064   0x633BA, состояние в SRAM 0x1526 / 0x1528 / 0x1531
     └─ 0x84360   опрос кнопок и машина состояний

задача 0x99CF8 → 0x86304 → 0x84100   отдельная ветка (0x63BE2)
```

### 0x84360 — машина состояний

Читает флаги круиза (индекс `0x574`) и ограничителя (`0x590`), маску кнопок
из `SRAM+0x1560` (биты проверяются по одному: `tst.w sl, #1 / #2 / #4 / #8`)
и состояния из `SRAM+0x1526`, `0x1528`, `0x1529`, `0x152A`. Выдаёт код
режима 1…7 и пишет его байтом в `SRAM+0x158C`:

| код | когда |
|---|---|
| 1 | состояние по умолчанию |
| 2 | `SRAM+0x152A` ≠ 0 |
| 3 | нажата любая из кнопок (биты 1/2/4/8 маски) |
| 4 | `SRAM+0x1526` ≠ 0 |
| 5 | `SRAM+0x1529` ≠ 0 |
| 7 | включён флаг круиза или ограничителя |

Дальше по `r4-1` идёт `tbb [pc, r2]` — таблица переходов на 6 ветвей.

### Про масштаб скорости

В `0x84360` значения из `SRAM+0x157A` и `SRAM+0x1572` (знаковые 16 бит)
пересчитываются как `ubfx r0, r0, #6, #8` — то есть **сдвиг на 6 вправо**
(деление на 64) с выделением 8 бит, диапазон 0…255.

Это делает версию «`26` и `200` — километры в час» правдоподобной: рабочий
масштаб даёт ровно такой диапазон. Но доказательством это не является —
неизвестно, сравниваются пороги с уже сдвинутым значением или с внутренним,
и что `0x157A` — именно скорость.

### Геттеры по типам данных

Обращения идут через несколько геттеров, различающихся способом чтения:
`0x48DC` (скаляр), `0x4904`, `0x494A`, `0x4978` (массивы — записи с
разрядностью 12 и n=2…4), `0x49C8`, `0x4A8C`.
